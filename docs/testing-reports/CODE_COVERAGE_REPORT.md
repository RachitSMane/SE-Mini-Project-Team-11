they count as 0 %. The whole-code-base figure (58.24 %) is therefore the honest lower bound.

## 5. Notable gaps and why they exist

| Gap | Reason | Mitigation |
|---|---|---|
| React UI (14 files, 2,165 lines) | no component-test library is in the project; adding one was out of scope for the final submission (no new dependencies) | 31 Playwright E2E tests drive every screen in a real browser |
| `server/src/recovery.js` 63 % (lines 17–35: rolling journalled clear/restore operations forward at start-up) | **measurement gap, not a testing gap:** `recovery.test.js` crashes the server and restarts it as a **child process** (`spawnServer` → `server/src/index.js`, `server/tests/helpers/harness.js`). Jest's V8 coverage records only the Jest process, so the roll-forward code that runs in the restarted child is not counted | `recovery.test.js` passes (TC-011, TC-024, TC-025): it asserts the board state after crashes at every step |
| `server/src/versions/versionService.js` 90 % | partly the same child-process effect (restore completion after a crash, lines 222–240); partly defensive paths: retry exhaustion, snapshot larger than the 16 MiB − 64 KiB guard (lines 77–79, 101–104) | crash paths: as above; the board-size limit that keeps snapshots below the guard is tested by `boardLimit.test.js` (TC-022) |
| `server/src/index.js` 0 % | process entry point; it **does run** — in the child processes of `recovery.test.js` and in every E2E run — but outside the Jest process | the failed-recovery exit path is asserted by `recovery.test.js` |

## 6. Limitations

- There is no coverage threshold in `jest.config.js` and CI does not run coverage; these figures are a
  measurement on 05-11-2026, not an enforced gate.
- No coverage was collected from the Playwright E2E runs or from server child processes started by
  `recovery.test.js`; code executed only there appears as uncovered.
- Figures depend on the V8 provider; the Babel/Istanbul provider would count statements differently.
