### 4.4 Error Handling, Logging & Monitoring

**Error handling principles**

- Every error returned to a client uses the common error object (§4.3) with a stable `code`; messages never contain stack traces, database details, tokens or other users' data.
- REST: a central Express error middleware maps errors to the HTTP statuses in §4.3; unknown errors become `500 INTERNAL` and are logged with the request ID.
- Socket.IO: handlers never throw to the client; they acknowledge `{ok: false, clientOpId, error}`. The connection stays open after operation-level errors; it is closed only for authentication failure, revocation, removal, board deletion (each preceded by `access:revoked`) or by the client after an acknowledgement timeout (§4.1.3).
- Persistence first: a database error while applying an operation causes rejection with `INTERNAL`, no acknowledgement of success, no broadcast and no change of `seq`, so clients never see an operation that was not stored (FR-027).
- Restore, clear and ownership transfer pause the board queue while they change state, so no operation is applied to a half-changed board (SD-02, SD-04).
- Snapshot too large (defensive, should not occur because of FR-008): the version is not written and `version.snapshot_too_large` is logged. Periodic or last-participant trigger: the Owner's client shows "This version could not be saved" and the live board is unaffected. Before-clear trigger: the clear is rejected (`INTERNAL`). Restore: the restore is rejected (`INTERNAL`).
- Version write failure (database error) follows the same rules: a clear or restore is never completed without its version (FR-007, FR-033). After its commit point a clear or restore is completed by the running task or by start-up recovery and is never reported as successful before completion (§3.6).

**Client reactions (COMP-01/02)**

| Situation | Client behaviour |
|---|---|
| `VALIDATION_FAILED`, `FORBIDDEN`, `OBJECT_NOT_FOUND`, `BOARD_FULL` on an operation | Remove the operation from `pending`, recompute the view, show a short message naming the reason (FR-026) |
| `RATE_LIMITED` | As above, with "You are sending changes too quickly" |
| `UNAUTHENTICATED` | Go to the login page (registered user) or the guest entry page (guest) |
| `access:revoked` | Show the reason (link revoked or expired, removed, board deleted) and leave the board |
| `role:changed` | Enable or disable tools for the new role without reload (FR-049, FR-050) |
| Connection lost | "Disconnected — reconnecting…" banner, tools disabled; after resynchronisation, notice if unconfirmed changes were discarded (FR-025) |
| REST `INVALID_TARGET` (transfer) | Keep the Members dialog open and explain that only Editor or Viewer members can become Owner |

**Logging (COMP-09)**

- Format: one JSON object per line, written by COMP-09 to the server's standard output, which the test environment and a deployment redirect to an append-only log file (`logs/server.log`). Common fields: `timestamp` (ISO 8601, UTC), `level` (`error`, `warn`, `info`, `debug`), `event`, `requestId`, `boardId`, `actorId`, `outcome`, `errorCode` and `durationMs` where relevant.
- `requestId` is the correlation ID: a UUID generated by COMP-03 for every HTTP request (and returned in the error object, §4.3) and by COMP-06 for every Socket.IO event it handles; Socket.IO entries also carry `socketId`. Entries written by start-up recovery have `requestId: null`.
- Security events (SEC-REQ-008): `auth.login_failed`, `auth.rate_limited`, `authz.denied`, `link.created`, `link.revoked`, `link.expired_disconnect`, `member.role_changed`, `member.removed`, `board.ownership_transferred`, `version.restored`, `board.deleted`.
- Operational events: `op.rejected` (with `errorCode`), `board.resync_requested`, `version.created`, `version.snapshot_too_large`, `version.restore_failed`, `version.restore_rolled_forward`, `op.clear_failed`, `board.clear_rolled_forward`, `recovery.required`, `db.write_failed`.
- Never logged: passwords, session or guest tokens, share-link tokens, `Authorization` headers, the e-mail address entered at login, board object content or text. The allow-list above enforces this for security events, and a redaction function removes these fields from all other entries before writing; TC-104 searches the log for them (Pass on 12-10-2026; historical v1.0 note: planned when this was written).
- Default level `info` in test and deployment; `debug` only on developer machines.

**Security event record (SEC-REQ-008, D13b).** The component that detects the event creates the record and passes it to COMP-09 (`log.security`): COMP-04 for `auth.login_failed`; COMP-03 for `auth.rate_limited` and REST `authz.denied`; COMP-06 for Socket.IO `authz.denied` and `link.expired_disconnect`; COMP-05 for link, member, ownership and board-deletion events; COMP-07 for `version.restored`. COMP-09 writes only the fields below (an allow-list; any other field is dropped) and adds `timestamp`.

| Field | Content | When not applicable |
|---|---|---|
| `event` | One of the security event types above | Always present |
| `timestamp` | ISO 8601, UTC, millisecond precision | Always present |
| `requestId` | Correlation ID of the HTTP request or Socket.IO event that caused the entry, plus `socketId` for Socket.IO; for an event raised by a server timer (link expiry), a newly generated UUID | Always present for security events |
| `actorType`, `actorId` | `user` with the account ID, or `guest` with the guest session ID, once a valid token or login has identified the requester | `actorType: "anonymous"`, `actorId: null` (failed login, missing or invalid token) |
| `boardId` | The board the event concerns | `null` (login events, rate limits not tied to a board) |
| `subjectId` | Internal account ID (`users._id`, never an e-mail address) of the account affected by the action: member whose role changed or who was removed, new Owner, or the registered account whose e-mail was entered at a failed login (COMP-04 looks the address up and writes only the ID) | `null` (no such account, or not relevant) |
| `outcome`, `reason` | `success` or `rejected`; for a rejection the error code of §4.3 (e.g. `UNAUTHENTICATED`, `FORBIDDEN`, `RATE_LIMITED`, `LINK_REVOKED`); a failed login always uses `UNAUTHENTICATED`, so the log does not say whether the e-mail exists | `reason: null` for successful events |
| `details` | Non-sensitive values only: `role`, `fromRole`, `toRole`, `linkId`, `restoredFrom`, `newVersion` | Omitted |

**Failed logins without account enumeration (SEC-REQ-006, SEC-REQ-008, FR-041).** Every failed login returns the same response, `401 UNAUTHENTICATED` with one generic message, whether the e-mail is unknown or the password is wrong — the bodies differ only in the per-request `requestId` (§4.3); for an unknown e-mail COMP-04 still runs one bcrypt comparison against a fixed dummy hash, a design measure intended to keep the response times of both cases similar; it does not prove constant-time behaviour, and response timing has not been measured (it is not part of TC-108). The login limiter counts failures per entered e-mail address (lower-cased), registered or not, so the 6th failure returns `429 RATE_LIMITED` in both cases. The limiter keeps only an HMAC of the address (key from an environment variable) in memory for 15 minutes; the address itself is never stored or logged. Only the server log, which is readable by operators and not by clients, records `subjectId` for a registered account.

**Monitoring metrics** (written to the log every 10 s and exposed on a development-only metrics endpoint)

| Metric | Purpose |
|---|---|
| `op_server_latency_ms` (receive → broadcast, per operation) | Server share of NFR-001 latency |
| `connected_sockets`, `participants_per_board` | Capacity (NFR-002) |
| `ops_rejected_total{code}` | Validation, authorisation, size and rate-limit rejections (SEC-REQ-003, -005, -006, FR-008) |
| `resyncs_total{reason}` (gap, reconnect), `resync_duration_ms` | Recovery behaviour (NFR-004) |
| `restore_duration_ms` | NFR-005 |
| `snapshot_bytes`, `board_content_bytes` | Early warning for the 15 MiB board limit and 16 MiB document limit (§3.6) |
| `http_requests_total{status}` | Error rate of the REST API |

`GET /api/v1/health` reports server and database status for test-environment checks (STP §6).
Metrics support diagnosis only; NFR results are measured by the STP harness, not by these metrics.
