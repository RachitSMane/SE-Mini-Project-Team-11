## 6. Test Environment

**Hardware:** one team laptop as the server host (application server and MongoDB); up to two
additional laptops on the same local network for multi-browser tests. Hardware specifications are
recorded in the test summary report with every performance result.

**Software:** Node.js LTS, MongoDB Community (local), current stable Google Chrome, Mozilla
Firefox and Microsoft Edge (versions recorded at test time), build of the system under test
identified by Git commit hash.

**Tools (DECISIONS.md D15):** Jest (unit tests), Supertest (REST integration tests),
socket.io-client scripted clients (Socket.IO integration, concurrency and latency harness),
Playwright (browser end-to-end tests and load timing), browser developer tools (network
throttling/offline simulation), MongoDB shell or Compass (database inspection), GitHub Issues
(defect tracking), GitHub Actions (CI, once configured).

**Implementation status of test assets:** the scripts, harnesses, seed data, fixtures, accounts and hooks named in this plan exist and were used in the execution of 12-10-2026 (Appendix A, `docs/IMPLEMENTATION_STATUS.md`). Historical v1.0 note: when this plan was written none of them existed; they were planned deliverables of the implementation phase and blockers for executing the corresponding test cases.

**Test hooks and configuration (test builds only, SAD §4.1.6):** `board-ready` performance mark;
`window.__wbTest.exportState()` and `submitRaw()`; `VERSION_INTERVAL_MS` (periodic interval for
tests — the configured value is recorded in every result, and the production value is 5 minutes, D11a); `LINK_EXPIRY_OVERRIDE_SEC`; `FAULT_INJECT` for TC-024 and TC-025; a separate test JWT secret in
`.env.test`. None of these is enabled in a deployed system.

**Performance measurement procedure (TC-009, TC-013, TC-019, TC-020):** the definitions of SRS §5
apply — start and end points, one monotonic clock per run (scripted clients in one Node.js process;
Playwright timings from the page's own performance timeline), nearest-rank percentiles, warm-up
excluded, rejected operations excluded from latency samples and reported separately, missing or
duplicate sequence numbers detected per client, and final states compared with a fresh
`board:join`. Raw samples and summaries are stored as CSV files under `test-results/` with the Git
commit, date, hardware, operating system, Node.js, MongoDB and browser versions, and are compared
with the targets of SRS §5.

**Test data:**

- **TB-STD** (DECISIONS.md D7a): 300 freehand strokes of at most 200 points each, 50 shapes and 20 text objects, generated by a seed script with a fixed random seed so every run uses identical content.
- Test accounts: one Owner, two Editors, one Viewer, plus guest sessions; passwords are generated by the seed script at run time and are not stored in the repository.
- Boundary data: stroke widths 0, 1, 20, 21; text of 500 and 501 characters; passwords of 7, 8, 72 and 73 characters; a 65,537-byte message (M1, just above the 65,536-byte limit); board-filling strokes produced by `gen-board-fill` with recorded M1–M4 sizes (TC-022); text containing `<script>alert(1)</script>`.

**Environment conditions for performance tests** (SRS §5, D7b): server and database on one laptop,
clients on the same machine or LAN, no artificial delay, no other heavy applications running.

## 10. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| NFR targets turn out infeasible when measured | Build the latency harness early; raise a change request for the affected NFR; report measured values honestly. |
| Timing measurements distorted by clock differences | Run all scripted clients in one process or on one machine. |
| Flaky concurrency tests | Fixed seeds, explicit waits on acknowledgements, repeated runs (10×) for timing tests. |
| CI not configured in time | Run the same commands locally before each push; record results in the PR description. |
| Shared laptop resources affect performance | Record hardware and background load; repeat runs; close other applications. |
| No deployed instance for TC-109 | Report TC-109 as Blocked (reason: no deployment, §13), never as passed. |

## 12. Suspension & Resumption Criteria

Suspend testing if:

- The test environment is unavailable for more than 4 hours.
- The build blocks more than 30% of the planned test cases.
- A Critical security defect is found (stop security sign-off until fixed).

Resume testing if:

- Blocking defects are fixed and verified.
- The environment is stable and the health check returns `ok`.
- Affected test cases are re-run from the beginning.
