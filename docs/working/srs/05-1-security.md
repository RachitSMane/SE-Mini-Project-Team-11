### 5.1 Security

#### 5.1.1 Security objectives

| Req ID | Security objective | Realised by |
|---|---|---|
| SEC-OBJ-001 | **Confidentiality of boards:** the content, participants and version history of a board shall be accessible only to its Owner, its members and holders of a valid, unexpired, unrevoked share link. | SEC-REQ-002, SEC-REQ-003, SEC-REQ-004, SEC-REQ-007 |
| SEC-OBJ-002 | **Integrity of board content and history:** board content and version history shall change only through validated operations by roles permitted to make them, and earlier versions shall never be altered. | SEC-REQ-003, SEC-REQ-005, FR-033 |
| SEC-OBJ-003 | **Accountability and abuse resistance:** security-relevant events shall be attributable to an account or guest session whenever one has been identified (and otherwise to their request), and no single client shall be able to degrade the service for other participants by flooding requests. | SEC-REQ-006, SEC-REQ-008 |

#### 5.1.2 Security requirements

| Req ID | Requirement (shall...) | Type | Priority | Acceptance criteria / Test case ref |
|---|---|---|---|---|
| SEC-REQ-001 | The system shall accept only passwords of 8 to 72 characters and shall store passwords only as salted hashes produced by an adaptive password-hashing function; passwords shall never be stored, returned or logged in plain text. | Security | High | Registration with a 7-character password is rejected; the stored user record contains a salted hash and no plain-text password; server logs contain no password. Test: TC-105 |
| SEC-REQ-002 | The system shall require a valid session token (registered users) or guest token (guests) for every request and real-time connection other than registration, login, link resolution and health check. Session tokens shall expire 24 hours after issue and become invalid at logout; guest tokens shall be valid for one board only and expire at the earlier of the link's expiry and 24 hours after issue. | Security | High | Requests and real-time connections without a token, with a tampered token, with an expired session or guest token, with a token used after logout, or with a guest token for a different board are rejected with "unauthenticated" (or "forbidden" for the other board); no board data is returned. Test: TC-106 |
| SEC-REQ-003 | The server shall check the requester's current role on the target board against the permission matrix (FR-051) for every request and every real-time message, using only server-side data to determine the role. | Security | High | **All** tested unauthorised modification attempts (100%) — through the request interface and through crafted real-time messages, including attempts that claim a different role or board in the payload — are rejected, are not stored and are not broadcast; all tested unauthorised read attempts return no board data. Test: TC-101, TC-102 |
| SEC-REQ-004 | Share-link tokens shall contain at least 128 bits of randomness from a cryptographically secure random generator, shall be stored only in hashed form, and shall be rejected after expiry or revocation. | Security | High | Generated tokens are ≥ 22 URL-safe characters (≥ 128 bits); the database holds only token hashes; expired and revoked tokens are rejected. Test: TC-103, TC-104 |
| SEC-REQ-005 | The server shall validate every request and real-time message against a defined schema (types, required fields, value ranges, maximum text length, maximum message size of 64 KiB (65,536 bytes per Socket.IO packet)) and shall reject non-conforming input; user-supplied text shall be displayed as plain text, never interpreted as HTML or script. | Security | High | Malformed and out-of-range messages, and a message of 65,537 bytes, are rejected without changing the board; a text object containing `<script>` markup is shown literally and no script executes. Test: TC-107 |
| SEC-REQ-006 | The system shall limit failed login attempts to 5 per entered e-mail address per 15 minutes, counted in the same way whether or not an account with that address exists, and board operations to 30 per second per connection, rejecting excess requests with a "rate limited" response. | Security | Medium | The 6th failed login within 15 minutes is rejected as rate-limited even with the correct password; the same happens for an unregistered e-mail address; for both addresses every failed attempt returns the same HTTP status, error code and message (only the per-request `requestId` differs); a client sending 100 operations in one second has the operations beyond 30 rejected, while every operation of the other participants is accepted. Test: TC-108 |
| SEC-REQ-007 | In any deployed (non-local) environment, all client–server communication shall use HTTPS and secure WebSockets with TLS 1.2 or later; plain HTTP requests shall be redirected to HTTPS. | Security | High | Deployment configuration review and a connection test confirm TLS ≥ 1.2 and the redirect. The local test environment is exempt and this exemption is recorded in the STP. Test: TC-109 |
| SEC-REQ-008 | The system shall record a security log entry for at least every authentication failure, authorisation rejection, share-link creation and revocation, member role change, ownership transfer, restore and board deletion. Each entry shall contain the event type, a UTC timestamp, the request correlation ID, the outcome and, for a rejection, a reason code; the actor (account or guest session ID) when known, otherwise the JSON value `null`; the board ID when the event concerns a board, otherwise `null`; and the internal ID of the account affected by the action (a member whose role changed or who was removed, a new Owner, or the registered account named at a failed login), otherwise `null`. Entries shall never contain passwords, session or guest tokens, share-link tokens, `Authorization` headers, the e-mail address entered at login or board content. | Security / Audit | Medium | After running the security test suite, the log contains an entry for each listed event type with every required field present; a failed login has actor `null`, board `null` and reason "unauthenticated", with the affected account ID only when the entered e-mail belongs to a registered account; a rejection carries a reason code; and a search of the log finds no password, token, entered e-mail address or board text. Test: TC-104 |

The values in SEC-REQ-001, SEC-REQ-002, SEC-REQ-005 and SEC-REQ-006 are recorded with their
rationale in DECISIONS.md D8a–D8d. The controls that implement each security
requirement are mapped in SAD §3.9.6 and the validating tests in STP §5.1.
